# 新仙剑打包与发布

目标：一份成果、一次必要检查、一个固定分享包，同时用于本地分享和GitHub。减少往返，不降低隐私要求。已有授权继续有效；技能本身不授权上传。

## 范围和复用

先读当前状态、公开克隆AGENTS.md与Git差异，确定本轮是玩家补丁、工具、文档还是美术。目录名不代表实际版本。工具更新不重建游戏，文档更新不重打二进制。先找已有包、报告和发布回执；不要遍历旧ZIP和全部历史候选。项目入口及命令见[项目参考](references/project.md)，需要时再读。

每项检查绑定覆盖文件的SHA256、检查方法/规则版本、验证脚本与证据文件。相同输入和方法可复用通过结果；存在旧报告或时间相同不够。文件变化只使相关检查失效，失败/缺少证据/未覆盖部分才补检。新脚本、资源和二进制仍要检查，离线结果不能冒充实机验收。

隐私分别覆盖变化文本、资源元数据、EXE及内嵌代码、最终包成员；文本初筛不能代替二进制内容检查。未变部分可复用匹配的既有证据。私有报告放公开树外，逐项判断新命中，不显示密钥原值；第三方合法署名保留。测试正则本身不等于真实凭据泄漏。

## 分享包和GitHub用同一份

先完成源码、说明与公开状态摘要，再固定明确文件清单。已有精确匹配的包优先复用；否则只生成一次。用`scripts/release_once.py`登记检查输入，或按明确清单生成ZIP及回执；它不会测试游戏、判断隐私或上传。

固定ZIP后按同一SHA256复制到本地分享目录，上传同一个文件。不要再做一份不同的“GitHub版”。只改Release描述不需重打包；包内内容变了才重新生成并补相关检查。新发布用新标签，不暗中替换旧附件。原版差分输入/资源/备份/下载的校验仍保留，传送器取消整EXE白名单不代表取消所有校验。

## 程序化发布与最少回核

保留用户README标题、图片和版式，只更新必要文字/链接。复用Git和已授权CLI，不操作浏览器或重复登录；现有连接没有附件功能则用GitHub CLI。只有无法程序化完成的必要一步交给用户。

一次审阅差异→固定清单→提交/推送固定提交→标签/Release→上传固定附件。远端分支/标签指向相同提交即可，通常不再逐blob下载全仓库。只在链接/图片改动或存在疑点时定向检查相应页面。

附件优先核服务器SHA256和大小；服务端没有可靠digest、不一致或确需验证下载链时下载一次。不要同时重复等价检查。网络重试前查远端，复用已上传同哈希文件；一次定向重试仍失败就记录具体待办，不反复新建版本/放宽检查。

## 收尾与续作

一次同步本地状态、工作记录、分享入口与公开摘要。回执记录版本/范围、固定提交、附件名/大小/SHA256、证据和远端URL/核验方式。私有路径、扫描细节和凭据不进入公开材料。

分别报告已构建、离线通过、实机反馈、本地安装、已上传、远端核验。未知状态续作先查回执和远端，不重新打包。公开文档用标签，本地记精确提交；不要为了回填自己的提交哈希再做第二个纯状态提交。最后只给下载入口、变化和必要未测项，不为报告重跑检查。
